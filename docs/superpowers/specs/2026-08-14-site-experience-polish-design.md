# 官网产品支持与服务页体验收尾设计

## 目标

在不新增后台、不改变反馈 API 和不重构整站的前提下，消除产品页重复反馈入口，提升反馈弹窗的信息清晰度，修复能力与服务页核心卡片的密集和截断问题，并为普通用户补足获得帮助的 FAQ。

## 已确认范围

- 两个产品页只保留一个主入口：`问题反馈与使用帮助`，点击后打开现有反馈弹窗。
- 删除产品页并排出现的“单独打开反馈页”；`/support/` 继续承担分享、直接访问和降级入口。
- 乐可点名安装帮助区保留面向开发者的 GitHub Issue 链接，但弱化为辅助入口。
- 弹窗标题显示产品名，产品锁定，桌面端居中、移动端全屏；表单成功与错误逻辑继续复用现有实现。
- 两个产品 FAQ 各增加一项普通用户帮助说明，指向页面内反馈弹窗和独立反馈页降级能力。
- 能力与服务页核心卡片桌面端使用两列，完整展示“解决什么问题、交付内容、适合谁、合作方式”，不再通过字符串截断制造省略号。
- 不修改服务内容、反馈数据结构、邮件、乐知、Turnstile、SEO 路由和产品代码。

## 组件边界

- `SupportDialog` 只负责弹窗交互、标题和独立页降级链接。
- 产品页只决定弹窗出现位置及开发者辅助链接，不重复实现反馈表单。
- `Services` 继续使用当前数据数组，仅重排卡片语义和视觉层级。
- 自动测试使用预渲染 HTML 契约验证入口文案、无重复链接、完整目标客户文本和响应式类名。

## 错误处理与降级

- 弹窗内持续提供 `/support/?product=<id>` 的完整反馈页链接，避免弹窗或安全验证异常时没有出口。
- 邮箱备用渠道继续由 `Support` 表单提供。
- GitHub Issue 仅面向开发者与开源贡献者，不作为普通用户主渠道。

## OSS 联动边界

- 本轮继续监控 `product-release-monitor.yml` 的自然执行。
- 若现有手工上传对象缺少自动化所需 SHA-256 元数据，工作流必须失败关闭，先通过测试修正兼容校验，再恢复镜像。
- 归个类 OSS 对象完成上传和回读校验之前，产品页继续使用 GitHub；验证成功后再单独切换为 OSS 主下载与 GitHub 备用下载。

## 验收

- 产品页不再显示“单独打开反馈页”。
- 两个产品均显示唯一的“问题反馈与使用帮助”按钮。
- 弹窗标题包含产品名，且包含“打开完整反馈页”降级链接。
- 服务页不存在人为截断目标客户的逻辑，核心卡片在桌面端两列、移动端单列。
- 相关测试先失败再通过，完整 `npm run verify` 通过。
- Draft PR 的 GitHub Actions 与 Cloudflare Preview 通过；未经额外授权不合并、不发布生产。
