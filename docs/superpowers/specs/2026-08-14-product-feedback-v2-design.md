# 官网产品反馈 v2 设计

## 目标

把现有“邮件反馈表”升级为稳定的产品反馈入口：产品页优先使用弹窗，独立 `/support/` 页面保留为可分享、可降级的完整入口；版本和平台来自官网审核过的正式发行数据；反馈在发送邮件通知的同时，以结构化记录交付乐知，供后续检索、归纳和产品迭代。

本阶段不建设工单管理面板，不规定小乐如何修改反馈状态，也不将乐知设计成工单状态的唯一事实来源。后续围绕状态管理和小乐交互另立设计。

## 已确认的产品体验

### 产品页弹窗为主

- 乐可点名和归个类产品页的“提交反馈”按钮直接打开反馈弹窗，不离开产品页。
- 桌面端使用居中对话框；窄屏设备使用接近全屏的对话框，保证表单控件和软键盘可用。
- 弹窗锁定入口产品，不要求用户重复选择产品。
- 关闭弹窗不清空产品页面状态；提交成功后在弹窗内展示反馈编号。
- 弹窗加载失败时提供“打开完整反馈页”链接。

### 独立反馈页保留

- `/support/` 保留完整反馈表，承担直接分享、邮件链接、搜索访问和弹窗降级。
- `/support/?product=leke-picker` 与 `/support/?product=guigelei` 用稳定产品标识预选产品。
- `product` 查询参数只是入口提示，不是安全凭证；后端始终校验实际提交的数据。
- 独立页切换产品时同步更新查询参数，避免地址与表单状态不一致。
- 产品中文名改变时不更换稳定标识；旧链接继续有效。

## 发行数据与联动选择

### 单一数据来源

反馈表不得单独手工维护版本和平台。它使用与产品页、SEO、下载链接相同的审核后发行数据。

现有 `src/products/releases.json` 只保存当前稳定版本，需演进为同时表达：

- 当前稳定版本；
- 已公开且仍接受反馈的历史稳定版本；
- 每个版本的发布时间、Release URL 和附件；
- 每个附件对应的平台、系统版本和架构。

自动发布监控继续只接受正式 GitHub Release，忽略 Draft、Prerelease、已删除版本及证据不完整的附件。发现新版本时追加历史记录并更新当前版本，不覆盖旧版本。

### 三级联动

表单顺序为“产品 → 软件版本 → 使用环境”。

- 产品确定后，只显示该产品的发行版本。
- 默认选择当前稳定版本。
- 版本确定后，只显示该版本真实提供或支持的环境。
- 乐可点名 v1.1.0 示例：Windows 10/11 64 位、Windows 7 SP1 64 位、Windows 7 SP1 32 位、在线版。
- 归个类 v1.6.0 示例：macOS 12 及以上、Apple Silicon。
- 始终提供“其他版本/不确定”和“其他系统/不确定”，避免阻止有效反馈。
- 切换产品或版本时，清除已不兼容的下级选择。

平台选项表示用户实际使用的发行目标，而不是泛化的操作系统列表；因此 Windows 10/11 可作为同一发行目标，Windows 7 的 32 位和 64 位应区分。

## 反馈数据模型

官网接收后生成一条结构化反馈记录，至少包含：

```json
{
  "schemaVersion": 1,
  "reference": "LK-20260814-XXXXXXXX",
  "productId": "leke-picker",
  "productName": "乐可点名",
  "releaseTag": "v1.1.0",
  "version": "1.1.0",
  "environmentId": "windows-modern-x64",
  "environmentLabel": "Windows 10/11 64 位",
  "issueType": "install",
  "description": "用户原始反馈",
  "contact": "用户填写的联系方式",
  "name": "用户称呼或空值",
  "submittedAt": "2026-08-13T16:47:00.692Z",
  "source": "lekeopen-support",
  "sourceUrl": "https://lekeopen.com/products/leke-picker/"
}
```

`reference` 是跨邮件、乐知和未来工单系统的稳定关联键。联系方式属于受限字段；公开索引、分析摘要和日志不得输出完整联系方式。

本阶段不在官网定义 `new/in_progress/resolved` 等处理状态，避免在没有管理入口时制造多个事实来源。状态模型留给下一阶段的反馈运营设计。

## 交付乐知

### 推荐边界

官网负责验证、生成反馈编号和形成规范记录；一个受认证的服务端适配器负责把记录交付到乐知。浏览器不得直接访问乐知，也不得持有乐知凭据。

处理顺序：

1. 校验来源、Turnstile、频率限制和表单字段。
2. 生成反馈编号与 UTC 原始时间。
3. 将结构化记录交付乐知，使用反馈编号实现幂等。
4. 发送邮件通知到 `contact@lekeopen.com`。
5. 只有必需交付均成功时向用户返回“反馈已收到”。

为避免出现“用户看到成功但反馈丢失”，乐知交付与邮件通知都必须有明确成功证据。若乐知暂时不可用，接口返回可重试错误，不在页面虚假显示成功。后续如引入持久队列，可改为“先可靠落盘、再异步投递”。

乐知目前没有已经确认可复用的“产品反馈工单”接口或状态模型；实施前必须在乐知侧定义最小、认证、幂等的接收契约，并验证小乐能够按产品、版本、环境、问题类型和时间范围检索。不得把普通全文入库冒充结构化反馈能力。

## 邮件通知

- 邮件仍发送到腾讯企业邮箱 `contact@lekeopen.com`，供即时提醒和人工回复。
- Resend 只作为发信服务及投递日志，不作为日常反馈后台。
- 标题继续包含产品、问题类型和反馈编号，便于搜索与归档。
- 邮件正文显示北京时间，例如 `2026年8月14日 00:47`。
- 内部记录继续保存标准 UTC ISO 时间，便于排序、跨时区和机器处理。
- 不在邮件中显示毫秒、`T` 或 `Z`。
- `Reply-To` 应指向用户填写且确认为邮箱格式的联系方式；非邮箱联系方式不得写入邮件头，避免邮件头注入和错误回复。

## 隐私与安全

- 延续 Turnstile、来源白名单、蜜罐字段、请求体限制和 KV 限流。
- 产品、版本和环境必须是服务端发布目录允许的组合；“其他/不确定”使用明确的保留值。
- 用户原始描述不得进入公开日志。
- 乐知接收凭据只存在于服务端 Secret。
- 官网隐私说明需从“仅通过邮箱接收、不另行保存”更新为：反馈会发送到支持邮箱，并作为受限结构化记录保存到乐知，用于问题处理、产品改进和必要记录；同时说明保留和删除原则。
- 用户继续被明确提醒不得提交学生名单、密码、私人文件或其他敏感信息。

## 错误处理与降级

- Turnstile 加载失败：显示可重试状态，并提供独立页或邮箱备用渠道。
- 发行目录不可用：页面保留“其他版本/不确定”和“其他系统/不确定”，不显示虚构版本。
- 字段组合失效：服务端返回字段级错误，前端刷新对应选项，不静默改写用户选择。
- 乐知或邮件发送失败：不返回成功编号页面；显示稍后重试和 `contact@lekeopen.com`。
- 重复提交：以反馈编号和服务端幂等机制防止重复入库；用户重试不能生成多条不可辨认记录。

## 可访问性与响应式要求

- 弹窗使用语义化 `dialog`，有标题、关闭按钮、焦点圈定和 Escape 关闭。
- 打开后聚焦标题或首个待填控件；关闭后焦点返回触发按钮。
- 移动端内容区域可滚动，提交按钮不被软键盘永久遮挡。
- 表单标签、错误提示和成功状态可被屏幕阅读器识别。
- JavaScript 或弹窗失败时，独立反馈页仍可访问。

## 测试与验收

### 自动测试

- 发行历史迁移和新 Release 追加，不覆盖旧版本。
- 产品、版本、环境三级联动及兜底值。
- 查询参数与产品选择同步。
- 弹窗焦点、Escape、关闭回焦和移动端布局契约。
- 服务端拒绝伪造的产品/版本/环境组合。
- 乐知幂等交付、超时和失败关闭。
- 邮件北京时间格式及安全 `Reply-To`。
- 隐私文案、SEO 和完整 `npm run verify`。

### Preview 验收

- 两个产品页分别打开正确产品的弹窗。
- 桌面和移动视口完成一条测试反馈。
- 乐知出现一条同反馈编号的结构化记录。
- Resend 显示投递到 `contact@lekeopen.com` 为 `Delivered`。
- 独立 `/support/` 页面和参数预选正常。

### 生产验收

- 合并后等待 GitHub Actions 与 Cloudflare 生产部署成功。
- 在生产执行一条已标注的测试反馈，核对页面成功编号、乐知记录和邮件 Delivered 三方一致。
- 运行只读 `npm run seo:inspect -- --json`，不得执行百度、IndexNow 或其他搜索平台真实提交。

## 分阶段范围

本设计实施内容：

1. 弹窗为主、独立页兜底的反馈体验。
2. 正式发行历史与产品/版本/环境联动。
3. 邮件北京时间和收件体验修正。
4. 结构化反馈安全交付乐知，并建立可检索证据。
5. 隐私说明、测试和 Preview/生产验收。

明确延期：

- 反馈管理面板；
- 工单状态与处理流程；
- 小乐修改状态、自动创建修复任务或自动回复用户；
- 跨产品趋势评分、聚类和版本规划自动化。

这些功能必须在结构化反馈稳定进入乐知后另行设计，避免一次引入未经验证的运营系统。
