# Site V1.4 Search Indexing and SEO Operations Design

## Status

Approved design for implementation planning. V1.4 remains open until both engineering acceptance and manual search-platform acceptance are complete.

## Goal

Move the official site from technically crawlable to operationally discoverable and measurable. Baidu is the first priority because the primary business is in China. Google and Bing remain first-class compatibility targets.

V1.4 must establish a maintainable workflow for ownership verification, sitemap submission, new-URL notification, production SEO checks, keyword governance, and recurring reporting. It must not claim that a search engine has indexed a page merely because a submission request succeeded.

## Current Baseline

V1.3 already provides:

- complete static HTML for every public route;
- unique titles, descriptions, canonical URLs, and one `h1` per page;
- structured data for organizations, pages, articles, projects, and breadcrumbs;
- generated `sitemap.xml`, `robots.txt`, and a non-indexable `404.html`;
- automated build validation for 26 indexed routes;
- China-first crawlability while remaining compatible with Google and Bing.

V1.4 reuses these outputs. It does not replace the React + Vite architecture or create a second route inventory.

## Delivery Strategy

Use an engineering-first, platform-second sequence:

1. Build and test all repository-side SEO operations capabilities without requiring account access.
2. Keep tokens and verification values in deployment configuration or environment variables.
3. Complete Baidu, Google Search Console, and Bing Webmaster Tools verification with the user operating login, CAPTCHA, and account confirmation steps.
4. Submit the production sitemap and perform one real supported URL notification on Baidu and Bing.
5. Record platform evidence and begin the recurring review cycle.

This sequence prevents account availability from blocking safe engineering work while preserving manual approval for external platform actions.

## Architecture

### Shared URL Inventory

The existing V1.3 SEO route manifest remains the source of truth. Sitemap generation, production inspection, and URL notification must consume the same public-route inventory or the built sitemap derived from it. No manually maintained duplicate URL list is allowed.

Only published, canonical URLs are eligible for inspection or notification. Draft content, preview URLs, query-string variants, and the 404 page are excluded.

### SEO Operations Tool

Add a focused `tools/seo-ops` layer with small commands for:

- production inspection;
- URL-delta calculation;
- Baidu URL submission;
- IndexNow submission for Bing;
- report generation;
- configuration validation and dry-run output.

Commands must be independently understandable and testable. Shared parsing, request, retry, redaction, and result-writing behavior belongs in small reusable modules rather than one large CLI file.

### Platform Responsibilities

- **Baidu:** verify site ownership, submit the sitemap, and use the official URL submission endpoint for new or changed canonical URLs.
- **Google:** verify ownership and submit the sitemap through Search Console. Do not use the restricted Google Indexing API for ordinary website pages.
- **Bing:** verify ownership, submit the sitemap, and use IndexNow for new or changed canonical URLs.

Ownership verification values must be configurable without hard-coding account secrets. Public verification files or meta values may be deployed when supplied by the platform, but private API tokens must remain outside Git.

## Data Flow

1. The normal production build generates static pages and `sitemap.xml` from the V1.3 route manifest.
2. SEO operations read canonical URLs from the generated sitemap or its shared source.
3. A URL-delta step compares the current public inventory with the last successful notification record.
4. Dry-run shows the exact provider, endpoint class, and URL set without making an external request.
5. A real run submits only eligible new or changed URLs and writes a redacted machine-readable result.
6. Production inspection fetches representative pages plus sitemap, robots, RSS, and an unknown route.
7. Report generation combines automated engineering evidence with manually entered or exported platform metrics.

Submission state records the URL, provider, timestamp, outcome, and retry eligibility. It never stores provider tokens or full sensitive response payloads.

## Production Inspection

The production inspector must validate:

- HTTPS and expected HTTP status;
- final hostname and redirect behavior;
- visible static body content in raw HTML;
- one `h1`, one canonical URL, and parseable JSON-LD;
- robots crawl permission and sitemap discovery;
- sitemap XML validity, canonical uniqueness, and route coverage;
- RSS availability;
- a real 404 status with `noindex`;
- internal links on inspected pages do not lead to broken same-origin targets;
- absence of development-only locator attributes in production HTML.

CI runs deterministic build checks and safe production reads. It must not require search-platform secrets or perform external URL submissions.

## Keyword and Internal-Link Governance

Create a maintainable keyword map covering:

- brand terms;
- core service and business terms;
- product and project terms;
- supporting engineering and news topics.

Each important page receives one primary intent and optional supporting terms. The map must identify conflicts where multiple pages target the same intent. Title and description changes should be limited to evidence-backed conflicts or missing positioning, not broad rewriting.

Core business, project, and relevant news pages should link to each other where the relationship helps a visitor. Internal links must be editorially meaningful and must not be generated as keyword-stuffed blocks.

## Content-Publishing Contract

Published content continues to require a title, summary, cover, publication date, and explicit published state. The existing build must continue to place published content into static pages, sitemap, RSS, and the publication queue.

V1.4 adds a release checklist for:

- search intent and title/description fit;
- canonical correctness;
- image and alt-text quality;
- relevant internal links;
- successful build inclusion;
- post-release inspection and URL notification eligibility.

## Error Handling and Safety

- Missing credentials force dry-run or configuration-error behavior; they never produce a success result.
- A failure for one URL does not discard successful results for other URLs.
- Network errors, HTTP 429, and retryable 5xx responses use bounded exponential backoff.
- Authentication and non-retryable validation errors stop the affected provider run with an actionable message.
- Logs redact tokens, secret query values, and sensitive response fields.
- Provider submission success means accepted for processing, not indexed.
- A page not yet indexed is an operations observation requiring a submission date and review date, not automatically an engineering defect.
- Broken canonical, robots, sitemap, or HTTP status behavior is a release-blocking engineering defect.

## Reporting

Provide a monthly SEO health-report template with:

- indexed-page counts by provider when available;
- impressions, clicks, representative rankings, and crawl errors;
- sitemap and notification status;
- production-inspection results;
- new or materially updated content;
- unresolved issues, owner, and next review date.

The repository may store templates and redacted reports. Raw account exports containing sensitive identifiers remain outside Git unless reviewed and intentionally sanitized.

## Testing and Verification

Automated tests cover:

- sitemap parsing and route eligibility;
- URL-delta calculation and deduplication;
- provider payload construction;
- dry-run behavior and missing-secret refusal;
- bounded retry behavior with mocked HTTP responses;
- token redaction;
- production-inspection assertions;
- report generation from stable fixtures;
- CI remaining free of external write requirements.

Acceptance also requires a clean full `npm run verify` run and a production read-only inspection after deployment.

## Manual Platform Acceptance

The user performs login, CAPTCHA, QR-code, and final account confirmation actions. Codex may prepare the exact page, verification value placement, and submission form, but does not bypass authentication.

Evidence required before V1.4 closes:

- Baidu ownership verified and the production sitemap accepted;
- Google Search Console ownership verified and the production sitemap accepted;
- Bing Webmaster Tools ownership verified and the production sitemap accepted;
- one real Baidu new-URL submission accepted;
- one real Bing IndexNow submission accepted;
- representative core pages show platform discovery or crawl evidence;
- unresolved indexing issues have an owner and dated follow-up record.

Search-engine indexing itself is asynchronous and outside release control. V1.4 may close when the engineering system works, platform submissions are accepted, crawl evidence exists, and remaining indexing latency is explicitly tracked.

## Completion and Rollback

V1.4 is complete only when repository automation, production inspection, documentation, and all three manual platform acceptance gates pass. Partial platform completion remains marked incomplete.

The implementation is additive. If a provider integration fails, disable that provider command or remove its deployment secret while retaining V1.3 static SEO behavior. No database or public API migration is required.

## Out of Scope

- paid search advertising;
- guaranteed rankings or guaranteed indexing dates;
- automated content generation for ranking volume;
- scraping search-result pages to bypass platform reporting;
- Google Indexing API use for ordinary pages;
- redesigning the public website or replacing the V1.3 rendering architecture;
- automatic publishing without human review.
